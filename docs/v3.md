# Prototype V3

V3 is built page by page. Each iteration adds one screen at a time under `src/v3/`; V2 stays untouched and keeps working.

## Routes

| Step | Path | Notes |
| --- | --- | --- |
| Landing | `/v3` | public |
| 1 Journey | `/v3/start` | preparing, newborn, return-to-work |
| 2 Role | `/v3/role` | parent, partner, caregiver |
| 3 Account | `/v3/account` | name, email, password, or Google |
| Sign in | `/v3/signin` | email and password, or Google |
| 4 Household | `/v3/household` | requires sign in; create, or join with a code |
| Home | `/v3/home` | requires sign in and a household; inside the app shell layout |
| Care log | `/v3/care-log` | same guard as Home; inside the app shell layout. `?log=feed` (or another type) opens the log panel and is then removed from the address |
| Sleep rota | `/v3/rota` | same guard and layout; local state only |
| Wellness | `/v3/wellness` | same guard and layout; local state only |
| Support | `/v3/support` | same guard and layout; local state only |
| Return to work | `/v3/return-to-work` | same guard and layout; local state only |
| Calendar | `/v3/calendar` | same guard and layout; local state only |

In create mode Step 4 also asks, all optional, for the baby's name, whether the baby is here or on the way, and the birth or due date. `babySummary()` in `src/v3/api/profile.js` turns these into a name and a line such as "6 weeks old" for the Home page.

After creating or joining, Step 4 shows an inline success state with a "Go to home" button to `/v3/home`. Signing in or creating an account with an existing household also goes to `/v3/home`. The V3 guard sends `/v3/home` visitors who are signed out to `/v3/signin` and those without a household to `/v3/household`.

## App shell and Home

`src/v3/layouts/V3AppShell.vue` is a router layout: a 264px sticky sidebar (logo, household chip, 7 nav items, privacy note, user row) and a main column with a 1120px content area. Under 992px the sidebar becomes a top bar with a menu button. The shell calls `useV3Home()` once and provides it to pages (`V3_HOME_KEY`), so the sidebar and page do not load twice. `useV3Home` reads the profile, household and members (`getHousehold`, `getHouseholdMembers` in `src/v3/api/profile.js`), each with a timeout.

The shell also calls `useV3Entries(householdId)` once and provides it (`V3_ENTRIES_KEY`), so Home and the care log share one live listener on `households/{id}/entries`. The listener waits for the household id (loading, never an error, until it exists), treats an empty collection as a normal empty snapshot, and reports `{ code }` on failure, with a 15 second watchdog that reports `timeout`.

Home is real data only. The main card reads "Log your first care entry" with a solid "Log care" button when there are no entries, or "Last feed {time}" with "Log a feed" and an outline "Open care log" when a feed exists. "Recent activity" lists the 5 newest entries (New badge for unseen partner entries) or "Nothing logged yet.". The Tonight card was removed until the rota page exists; there is no sample data, no "Sample" badge and no `homeSample.js`. The butter "Yours alone" check-in box stays.

All seven sidebar items now link to V3 pages (`src/v3/data/nav.js`). The Home "Check in privately" button goes to `/v3/wellness`.

## Firestore collections

- `users/{uid}`: displayName, email, photoURL, journey, role, householdId, onboarded, createdAt, lastSeenAt
- `households/{id}`: memberIds, inviteCode, journey, createdBy, createdAt, babyName (string or null), babyStatus (`born` or `expected`, default `born`), babyDate (`YYYY-MM-DD` or null; date of birth or due date)
- `households/{id}/members/{uid}`: displayName, photoURL, role, joinedAt
- `invites/{code}` (code looks like `NT-XXXX`): householdId, createdBy, createdAt

## Owner setup in the Firebase console

1. Authentication, Sign-in method: enable Email/Password (Google is already used by V2). Create the Firestore database (Build, Firestore Database).
2. Deploy the rules in `firestore.rules` (Firebase CLI: `firebase deploy --only firestore:rules`, or paste the file into the Rules tab and publish).

## Working rule

V3 is built page by page: logic and rules first, then one page UI at a time in `src/v3/pages/<name>/index.vue`, shared pieces in `src/v3/components/`.

## Landing layout

The V3 landing follows a Z pattern: top bar, then a hero row (copy and the only solid plum button on the left, a decorative coded preview on the right), then a "Where are you right now?" row of three link tiles, then a final row with the handover message on the left and an outline "Set up your household" button on the right. The preview is `aria-hidden` and uses `TonightTimeline` with a fixed time of 9:40 PM, inside a single white panel.

## Care log

`src/v3/pages/care-log/index.vue` reads and writes real Firestore data in `households/{id}/entries` (fields in `docs/data-model.md`). Home links here with "Log a feed" (`?log=feed`), "Open care log" and "View full log".

Files:
- `src/v3/api/entries.js`: `addEntry`, `updateEntry`, `deleteEntry`, `markSeen`, `subscribeEntries` (live, newest 50), `loadOlder`.
- `src/v3/api/entryHelpers.js`: pure helpers (`ENTRY_TYPES`, `summariseEntry`, `groupByDay`, `todayStats`, `lastOfType`, time formatting). No Firebase imports.
- `src/v3/components/CareLogPanel.vue`: the right-side log and edit panel (a dialog; chips only, time never in the future). `V3ChipGroup.vue` is its radio-style chip row.
- Icons added to `V3Icon`: feed, diaper, note, medication, edit, trash, plus, check, x.

Load errors are logged with `console.error("[v3 care log]", error.code, error)` and shown by cause (`describeEntriesError` in `entryHelpers.js`): `permission-denied` means the entries rules in `firestore.rules` are not published yet, `failed-precondition` means a missing index, `unavailable` or timeout shows the connection message, anything else shows the code in a muted line. Failed mark-as-seen writes are only logged. The filter chips and the panel chips share `.v3-chip` in `v3.css`, which `V3AppShell`, the care log, Home and the chip components import themselves so the styles never depend on which page loaded first.

Behaviour: the timeline updates live. Entries by the partner that you have not seen show a "New" badge for the current visit; they are marked seen (`seenBy.<uid>`) shortly after they appear and the badge is gone on the next visit. Edit and delete exist only on entries you created. Delete asks inline ("Delete this entry?"). Undo is intentionally not built.

Rules (`firestore.rules`, under `households/{id}/entries/{entryId}`): members read; members create entries with `by` equal to their uid, a known type and a timestamp `at`; the author may update any field (but not change `by`); any member may update only their own key in `seenBy`; only the author deletes. Rules are not yet tested in the emulator. The query orders by `at` only, so it needs no composite index.

## Sleep rota, Wellness, Support, Return to work and Calendar (local only)

These five pages have no Firestore. State lives in Pinia stores that persist to localStorage (every read and write is in try/catch, so a blocked storage falls back to memory):

| Key | Store | Holds |
| --- | --- | --- |
| `nt.v3.rota` | `src/v3/stores/rota.js` | `pattern` (alternate, split, manual), `firstOnDuty`, `startDate`, `handoverTime`, `overrides` (date to me, partner or open), `swaps` |
| `nt.v3.checkins` | `src/v3/stores/checkins.js` | one `{date, mood 1-5, stress 1-5, savedAt}` per day, replaced when saved again the same day |
| `nt.v3.rooms` | `src/v3/stores/rooms.js` | pumping rooms added by the user (status "needs verification") |
| `nt.v3.rtw` | `src/v3/stores/returnToWork.js` | `returnDate`, `tasks`, `responsibilities` (area key to me, partner, both or null) and `pumping` (checklist, sessions, times) |
| `nt.v3.calendar` | `src/v3/stores/calendar.js` | `events` array (title, date, endDate, allDay, start, end, owner, type, notes) |

Because the data is per browser, nothing syncs between the two parents yet.

Sleep rota: the plan is generated from the settings by the pure helpers in `src/v3/api/rotaHelpers.js` (`weekNights`, `restSummary`, `suggest`, `applySwap`, `resolveSwap`, `cancelSwap`). Pending swaps do not change the plan; accepted swaps do. A swap has `date` (a night the `from` person gives away) and `withDate` (a night they take, or null for nothing in return). "Apply suggestion" applies an accepted swap at once because nobody else can answer yet; once a database exists it should create a pending request instead. Partner requests cannot arrive until then, but Accept and Decline are built and tested. Names come from the household the layout provides ("Me" and "Your partner" as fallbacks).

Wellness: mood and stress only, saved privately on this device. Mood "Very low" or stress "Very high" shows a gentle note linking to Support. There is no "private" info box on the page by design.

Support: Guides reuse the V2 help content (`src/data/help.js`, imported). Trusted resources reuse the V2 Help side panel contacts (`src/v3/data/support.js`); they are unverified and the page says so. Pumping rooms use the two sample rooms in `src/v3/data/pumpingRooms.js` (SAMPLE DATA, not confirmed) plus rooms stored in `nt.v3.rooms`. The map is a Google Maps embed iframe for the selected room; "Add to Google Calendar" opens a prefilled Google Calendar event in a new tab (helpers in `src/v3/api/roomHelpers.js`).

Shared pieces: `src/v3/components/V3Tabs.vue` (underlined tab bar with arrow keys; the page renders the tabpanels).

## Return to work

`src/v3/pages/return-to-work/index.vue` is a guided planner, not a dashboard: the first thing is the return date line, then the ordered "Next steps" list. Tabs: Plan, Responsibilities, Pumping preparation.

- Plan: with no date, "When do you go back?" and the page's one solid button, "Save date" (it becomes outline while the add task form is open). With a date, one sentence ("Back at work on 4 November. 21 days to go.") and a "Change date" text button. Tasks are grouped Overdue, This week (today and the next six days), Later, No date and Done, with empty groups left out, sorted by due date then title. Each task has a checkbox, owner badge, group, due text, edit and delete (inline "Delete this task?" confirm). "Add a task" opens an inline form. "Suggestions" lists six fixed prompts (`src/v3/data/rtw.js`) that the user adds with one tap (owner both, no date); an added suggestion disappears. There is no sample data; the empty state says "No tasks yet. Add one or start from the suggestions below."
- Responsibilities (draft): eight areas, each with an owner chip row (Me, partner, Both, Not decided), a summary line, a hint when one person has 2 or more extra areas, and "Make a task" which adds a task with the chosen owner (both when undecided).
- Pumping preparation (draft): five checklist items with "n of 5 done", breaks per workday (2 to 4) and time of day chips with a summary, and a rooms list that reuses `SAMPLE_ROOMS` plus rooms saved in `nt.v3.rooms`. "Open in Support" goes to `/v3/support`; the Support page has no query for its pumping tab yet, so the link opens its first tab.
- Pure helpers (`src/v3/api/rtwHelpers.js`): `daysUntil`, `returnSentence`, `dueText`, `groupTasks`, `ownerCounts` (open tasks only), `suggestedTasks`, `responsibilityCounts`, `balanceHint`, `pumpingSummary`. Components: `RtwResponsibilities.vue`, `RtwPumping.vue`.

## Calendar

`src/v3/pages/calendar/index.vue` is a shared month calendar in the TimeTree style, with a Month and Agenda switch (chips, no tabs). Nothing syncs between the parents yet.

- Month view: Monday first, 6 weeks. Each cell shows the date (today is a plum circle), up to two single-line chips coloured by owner (me apricot, partner powder, both gray with a plum left border; the owner name is also in visually hidden text), "+n more", and a small moon with the initial of whoever is on night duty (`aria-label="Night duty: {name}"`). Night duty is read from the sleep rota store through `nightOwner` in `src/v3/api/calendarHelpers.js`. Multi-day events show as a chip on each day. Under 768px the chips become owner coloured dots and the day panel is a bottom sheet.
- Day panel: `src/v3/components/CalendarDayPanel.vue`, a dialog like `CareLogPanel` (Escape closes, focus returns, focus is trapped). It lists the day's events with edit and delete (inline confirm) and holds the add and edit form: title, All day switch, start and end date (added so multi-day events can be made), start and end time, owner chips, type chips (Appointment, Family, Work) and notes (280 characters). "Add event" in the toolbar opens it in add mode for the selected day if that day is in the month shown, otherwise today, otherwise the first of the month shown.
- Agenda: events from today, grouped by day. Empty state "No events yet. Add the first one.".
- Planned, not built: Google Calendar sync (V2 notes and `docs/design.md` describe the intent) and moving events and the return to work plan to Firestore so both parents share them.
